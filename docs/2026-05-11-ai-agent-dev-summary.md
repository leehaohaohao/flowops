FlowOps 是由 AI Agent 辅助开发的自托管 CI/CD 平台，技术栈为 Spring Boot 加 Thymeleaf 加 MySQL，通过命令行调用 Docker 管理容器。项目历时十三天，七十七次提交，产出二十七个 Java 源文件，覆盖认证鉴权、服务管理、容器编排、代理配置、实时日志及仪表盘统计等完整链路。

开发分三个递进阶段。第一阶段搭建项目骨架，包括数据库表设计、MyBatis 数据层接入、Sa 认证集成。最棘手的是认证拦截器重定向死循环，未登录请求被反复导向登录页又触发拦截。传统调试难以定位，因问题在框架隐式行为而非业务逻辑。最终通过排除路径、启用 Cookie、切换 JWT 三步解决。AI 写代码极为高效，但面对框架隐式行为引发的问题，仍需开发者提供排查方向，人的主导不可缺。

第二阶段实现核心部署能力，涉及制品上传、模板生成、容器管理三大模块。关键决策是放弃 Docker SDK 改调命令行。起初 SDK 遇到版本冲突和依赖污染，AI 分析后建议改用命令行，代码量缩减过半且消除了升级维护负担，是做减法优于做加法的思路。后续还解决了命令语法兼容、容器操作宿主机引擎、健康状态轮询等工程细节。这些问题都属于环境适配类，AI 拿到明确报错后通常一至两轮即可修复，充分体现了报错驱动开发的效率优势。

第三阶段聚焦体验打磨。仪表盘接入真实数据而非静态占位，代理规则从写死单条演进为动态增删的灵活模式，WebSocket 日志从空存根实现为实时推送链路，涉及文件异步读取、会话管理等跨层逻辑，均由 AI 一次性完成。

回顾开发过程，AI 辅助开发展现出三个核心优势。其一是效率指数级提升，同类项目传统需四到六周，实际不到两周完成。其二是持续记忆，通过记忆系统记住架构决策，无需重复解释。其三是报错修复极快，从发现到修复数分钟完成，传统查资料试错难以比拟。

实践也揭示了 AI 的边界。架构决策如技术选型、模块粒度、接口设计，仍需人类判断，AI 可分析但无法替代。测试验证不可托付，AI 代码可能隐含边界遗漏或环境假设，须实测验证。需求澄清更易被忽视，模糊的描述会让 AI 自由发挥而非追问，偏离真实意图，因此前期需求拆解是保证协作质量的前提。

综合实践提炼五条方法论。第一，保持项目文档及时更新，记录架构决策形成长期记忆。第二，编码前善用计划模式确认方案，避免边写边改。第三，每模块即提交，便于回退和上下文管理。第四，面对缺陷先确认复现步骤，收集错误信息再交给 AI，输入质量决定输出质量。第五，代码审查不可省略，AI 代码风格一致，但业务逻辑仍需人工逐条确认，尤其是状态变更和外部交互的关键路径。

FlowOps 的成功证明，AI 已具备承担全栈项目多数开发工作的能力，从持久层到前端均能交付可用的代码。但项目成功仍建立在人对需求的理解、对架构的判断及对产出物的持续验证之上。人机协作并非取代关系，而是能力放大器模式，关键在于找到各自擅长领域并建立高效协作节奏。
