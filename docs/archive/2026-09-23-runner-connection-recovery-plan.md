## 目标和边界

子节点可先于主节点启动。主节点不可达时，子节点保持运行，定期尝试连接；主节点上线后自动完成带 token 的注册并开始心跳与接收任务。已注册连接中断后，也应重新连接、重新注册，恢复在线状态。进程收到退出信号时立即停止等待和重连，并正确清理当前连接。

保持当前轻量 Go 执行器形态，不增加数据库、常驻队列或额外服务。重连只恢复**连接和接收新任务的能力**；未收到确认的旧任务不能因为重连而自动重复执行。任务持久化、断点续传、消息重发和部署幂等性另立计划。

## 设计决策

1. **子节点主动重试**：进程只创建一个连接管理循环。每次尝试均使用新的连接/会话；连接成功后先注册，注册成功才启动心跳和任务接收。任一环节失败，关闭本次连接，等待后重试。
2. **有界退避**：建议初始等待 1 秒，指数增长至最多 30 秒，并加少量随机抖动；单次拨号和注册均有明确超时。等待由 `context.Context` 控制，停止信号可立即打断。成功注册后重置退避。
3. **区分错误**：连接拒绝、超时、EOF 等网络问题持续重试；明确的 token 错误、节点未登记、缺少配置等配置/认证错误应报出清晰原因并停止自动重试或进入低频受控等待，不能每秒刷请求。最终行为由执行器与协议负责人在实现前统一错误类型，不能仅靠错误字符串匹配。
4. **一次会话一套协程**：心跳、读取循环、产物接收共用会话生命周期。旧连接退出后，先停止旧心跳/读取、清理连接和临时状态，再开始下一次注册。防止重复心跳、两个 goroutine 同时读同一连接、旧会话向新连接回写。
5. **协议会话身份先认证后接管**：Master 校验新连接注册成功后，再原子替换同 `runnerId` 的旧会话；拒绝新连接不影响旧会话。认证失败响应应先可靠发出，再关闭未认证连接。旧连接的断开事件不得误删新会话或把新节点标成离线。
6. **任务处理采用保守语义**：断线时正在执行的 Docker 命令如何停止/等待、结果无法回传时如何记账，要明确定义并测试；本期不自动重放任务。主节点现有掉线失败化逻辑继续作为超时/失联保护，避免重复执行部署动作。

## 协议侧身份与超时事件专项修复（主体已实现，竞态待修复）

这项工作涉及 `nexa-protocol/java` 与 `flowops` 后端，应在真实主子节点联调前完成。无需修改 Protobuf 消息结构。协议侧已加入发送连接鉴权，后端已按会话身份记账心跳；断开回调的会话归属仍须按下文 D 修复。

### A. 所有已注册消息以发送 channel 绑定的会话为准

- 为协议 handler 提供统一的会话解析/校验入口：从 `ctx.channel()` 取得注册后绑定的 runnerId，查 `SessionManager`，并要求当前会话的 channel 与 `ctx.channel()` **完全相同**。未注册、已被新连接接管或不匹配的连接不得刷新状态、返回业务回执、移除会话或触发业务回调。
- `HeartbeatHandler` 用该会话更新心跳、向**发送方当前会话**回包，再调用 listener；报文中的 runnerId 仅作一致性检查，不作为会话选择依据。伪造他人 runnerId 的心跳不得刷新任何节点，也不得污染负载。
- 按同一规则检查 `DisconnectHandler`：只能条件移除**自身当前会话**；不能依据报文 runnerId 删除别人的会话，也不能由旧连接断开触发新会话的离线处理。
- `TaskResultHandler`、`ContainerStatusHandler`、`ContainerLogsHandler` 也必须按发送 channel 解析会话，并核对响应中的 runnerId；避免伪造任务回执或污染其他节点的查询结果。`ArtifactHandler` 现有的 channel 校验应保留，并与统一规则对齐。
- `Envelope.source_id` 与 payload 中的 runnerId 均是客户端提供的数据，可用于一致性检查，不能代替 channel 到会话的绑定。`RegisterHandler` 仍是唯一允许未认证连接处理的注册入口。

### B. 超时事件只处理被确认移除的那次会话

- `HeartbeatMonitor` 对过期会话先使用 `removeIfPresent(runnerId, session)` **条件移除**；只有成功移除当前映射时才关闭该会话并发出一次超时断开事件。若已被新会话接管，则只清理过期的旧连接，不通知新节点掉线。
- 调整 `channelInactive` 和主动 `DISCONNECT` 处理，与超时监控共用“仅条件移除成功才通知”的规则，避免双重通知。覆盖超时、主动断开、网络断开与新旧连接交错。
- 仅调整调用顺序仍不足以彻底消除竞态：`NexaMasterListener.onDisconnect(String runnerId, String reason)` 没有会话身份。协议负责人需设计携带 `RunnerSession` 或会话代次的回调，并使后端只失败化属于该次会话的待处理任务/查询；同步评估旧回调 API 的兼容方式。只凭 runnerId 加查询当前会话的守卫属于过渡方案。

### C. 测试与验收

| 测试场景 | 必须验证的结果 |
|---|---|
| 未注册 TCP 连接发送已在线节点的心跳；已注册 A 发送 B 的 runnerId | B 的心跳时间和负载不变；A/B 均不收到错误归属的心跳响应 |
| 未注册或 A 发送 B 的主动断开、任务回执、状态/日志回执 | B 会话及待处理任务/查询不受影响；业务 listener 不以 B 身份处理该消息 |
| 旧连接被同 ID 新连接接管后继续发送任何已注册消息 | 旧连接被拒绝；新会话、心跳与任务保持正常 |
| 超时扫描与新连接接管交错；`channelInactive` 同时发生 | 只对真正被移除的旧会话通知一次；新会话不被标记离线，所属新任务不失败化 |
| 真实节点正常心跳、主动断开和超时 | 心跳可持续保活；两种断开路径各产生一次正确事件，重连后可正常收新任务 |

Java 协议库已增加使用不同 `EmbeddedChannel` 的处理器测试及超时与接管并发测试；还须补充下文 D 的确定性交错测试。后端须补充会话代次相关测试。修复后重新运行协议与后端回归，再进行真实 Go 子节点联调；全部通过后才可把专项修复标记为完成。

### D. 2026-09-23 复核发现的剩余竞态与修复计划

1. **超时标记与连接退出交错时，断开通知可能漏发（`nexa-protocol/java`）——已修复（协议 v0.6.2）**。
   原问题：`HeartbeatMonitor.doCheck()` 先执行 `session.markTimedOut()`，再调用 `removeIfPresent`；
   若 `channelInactive` 恰在两者之间抢先移除该会话，它会因为 `session.isTimedOut()` 为真而跳过回调，
   监控器随后因移除失败也不回调，会话已离线却收不到掉线事件。
   **修复方式（统一事件所有权）**：三条断开路径共用「**谁成功条件移除当前会话，谁负责通知恰好一次**」——
   `channelInactive` 不再凭 `isTimedOut()` 推断“监控器已通知”而跳过；`markTimedOut` 仅用于标记状态与
   决定上报原因（超时 → `heartbeat_timeout`，否则 → `connection_lost`）。协议侧新增确定性交错测试
   `TestTimeoutAndConnectionCloseInterleavingNotifiesOnce` 固定“标记超时 → 连接退出移除 → 监控器移除失败”
   顺序，断言恰好一次通知且携带会话身份。
2. **旧会话回调可能清理新会话工作（`flowops` 后端）——已修复（2026-09-24）**。
   原问题：`FlowOpsMasterListener.onDisconnect(RunnerSession, String)` 立即退化为 runnerId；
   `RemoteTaskManager.failTasksForNode`、`QueryManager.failPendingForNode` 和节点离线写入均按 runnerId 操作。
   旧会话条件移除成功与回调执行之间，新会话仍可完成注册并接收任务，旧回调此时会失败化同 ID
   新任务/查询，且可能把新节点标离线。
   **修复方式（以协议会话注册表判定归属）**：
   - 新增 `service/node/SessionTracker`：注册成功时为该连接分配唯一的**代次标签**并写入
     **channel 属性**（随 channel 回收，不泄漏）。**代次仅作日志诊断，不作归属比较**
   - `onDisconnect(RunnerSession, String)` 在**按节点临界区**内读取协议会话注册表：事件会话已被条件移除，
     注册表中若仍有会话则必是接管者 → 跳过清理；注册表为空 → 执行清理
     （失败化任务/查询、清负载、写离线快照）。旧签名 `onDisconnect(String, String)` 用同一条规则
   - 注册与断开在同一把按节点锁（`SessionTracker.withRunnerLock`）内互斥，避免重复清理与 DB 状态写入乱序
   - **为什么不能用代次比较（2026-09-24 复核补充）**：后端 `onRegister` 回调先分配代次并释放锁，
     协议 `RegisterHandler` 随后才 `sessionManager.register` 写入注册表。两个同 ID 连接并发注册时，
     代次分配顺序可能与最终生效的会话顺序相反（注册表里最后一次 register 才是当前会话）。
     按代次比较会把真正在线的会话判为旧代次，**整体跳过任务/查询失败化与离线写入**。
     以注册表判定则与分配顺序无关
   - **确定性交错用例**：
     - `FlowOpsMasterListenerReconnectTest#liveSessionWithOlderGeneration_isStillCleanedUp`：固定
       “A、B 依次回调（A 标签更小）→ 协议最终注册 A → A 被移除并回调”，断言清理照常完成
       （回归证明：临时改回代次比较，该用例立即失败）
     - `#takeoverBetweenRegistryCheckAndCleanup_scopesFailureAndRepairsSnapshot`：固定
       “读完注册表(空) → 新会话注册成功 → 继续清理”，断言清理仍按事件会话代次归因、离线快照被复查修正回在线
       （回归证明：去掉写后复查，该用例立即失败）
     - `#supersededSession_isSkippedWhileSuccessorIsLive`：接管者在线时，旧会话迟到事件不失败化任务/查询、
       不清负载、不写离线
     - 另有当前会话断开/心跳超时仍失败化并写离线、旧签名与未绑定代次的注册表判定用例
   - **“读注册表 → 清理”窗口的处理（2026-09-24 第二轮复核补充）**：
     - **任务/查询按会话代次归因**：`PendingTask.sessionGeneration`（下发时取协议注册表当前会话代次）与
       `QueryManager.PendingQuery.sessionGeneration`（发起时同源）；`failTasksForNode` /
       `failPendingForNode` 只失败化**代次完全相等**的工作。接管者即使恰在窗口内注册并立刻收到新任务/查询，
       也不会被旧会话的清理误伤（由 `RemoteTaskManagerTest` 4 例、`QueryManagerTest` 2 例覆盖）
     - **离线快照写后复查**：写完离线后立即复查注册表，若已有接管者则修正回在线，
       把该窗口压到两次写入之间；快照本身为“最后已知状态”，权威在线状态按实时会话计算且 ≤10s 心跳自愈
     - 若要连最后这段窗口也彻底消除，需要 DB 侧按会话代次做条件更新（`nexa_node` 增代次列），
       属可选加固：该窗口不影响鉴权、任务/查询归属与前端展示

**关闭条件**：上述确定性交错用例通过（D.1 协议侧 v0.6.2 用例；D.2 后端含“代次顺序相反”“接管者在线”
“读注册表→清理窗口”三例，另有任务/查询归因用例），原有协议身份/超时测试与后端回归通过，
并记录真实节点重连联调结果。当前状态：
“鉴权主体、后端会话归属与工作归因（注册表 + 代次）、协议侧事件所有权均已实现，仅剩真实联调”。

## 验收场景

| 场景 | 期望结果 |
|---|---|
| 子节点先启动，主节点端口未监听；之后主节点启动 | 子节点存活并按退避重试；主节点上线后仅注册一次，心跳和任务接收正常 |
| 主节点接受 TCP 但不返回注册响应 | 单次尝试到时退出，连接释放，进入下一轮；无永久卡死 |
| 已注册后主节点进程停止，再启动 | 子节点检测到断线，停止旧会话并自动重新注册；前端/后端在线状态最终恢复 |
| 网络瞬断，旧会话与新会话短暂重叠 | 只有一个有效会话；旧连接关闭不移除新会话，也不将新会话标记离线 |
| 错误 token 或节点未登记 | 拒绝原因清晰；不会反复高频请求，不会接收任务；同 ID 的合法在线会话保持正常 |
| 未注册连接或已注册 A 冒用 B 的 runnerId 发送心跳/断开/回执 | B 的心跳、负载、会话、任务与查询结果均不受影响；协议拒绝该消息 |
| 旧会话超时与新会话注册交错 | 仅旧会话收到一次断开处理，新会话保持在线且新任务不被失败化 |
| 等待重试时收到 SIGINT/SIGTERM | 立即退出，不继续拨号；已连接时尽力发送断开消息并关闭连接 |
| 已恢复连接后发起远程部署 | 实际 Go 子节点拉取并校验产物、执行 Docker Compose、回传结果；状态和日志查询能返回该节点结果 |
| 执行任务或传输产物时断线 | 不自动重复执行原任务；主节点记录可解释的失败/超时，子节点重连后能接收后续新任务 |

## 实施审阅要点

- 在代码评审中明确 **`Runner.Start` 的返回语义**：是启动并返回，还是阻塞直到停止。主循环只能有一个所有者，避免 `main`、runner 与 Go Client 分别发起重连。
- 心跳写失败和消息读失败都应把错误交给同一个连接管理循环。注册未完成前不得对外显示节点在线。
- 复核执行器单连接上的消息分发：目前产物接收会直接读取同一连接，并忽略期间到达的其他消息。恢复连接前要清理传输状态；若联调出现并发查询/任务丢失，另行设计单一读取者与请求分发，不把扩大协议范围塞进最小恢复改动。
- 明确部署节点地址的配置来源。`nexa.master.host=127.0.0.1` 仅适合本机联调；生产跨机部署应配置可到达地址和端口，并通过环境检查确认防火墙、路由和 token 配置。
- 同步修正执行器 README 的环境默认值：文档写默认 `dev`，`main.go` 实际默认 `prod`。配置文件加载失败应给出明确错误，与暂时连接失败分开处理。
