# FlowOps 优化建议与分阶段实施计划

> 日期: 2026-05-12

## 阶段一：安全加固（优先级最高）

**目标**: 消除所有可被直接利用的安全漏洞

**建议分支**: `fix/security-hardening`

| 序号 | 任务 | 对应 Review 问题 |
|------|------|------------------|
| 1 | 引入 BCrypt，密码存储和校验改用加密哈希 | #1 明文存储密码 |
| 2 | 敏感配置外部化：数据库密码、JWT 密钥改用环境变量，prod 配置文件脱敏 | #2 敏感信息硬编码 |
| 3 | LogController content 端点增加路径遍历防护，校验 filename 不含 `..` 且在允许目录内 | #3 路径遍历风险 |
| 4 | 登录接口增加验证码校验（项目已有 captcha 端点，需确认是否启用）或失败次数限制 | #4 无暴力破解防护 |

**验收标准**:
- 所有新密码 BCrypt 加密存储，旧密码可兼容（提供迁移脚本或强制重置）
- `application-prod.yml` 中无明文密码，启动时从环境变量读取
- 路径遍历 payload（如 `../../etc/passwd`）请求返回 400/403
- 连续 5 次错误密码后账户临时锁定或要求验证码

## 阶段二：稳定性与数据完整性（高优先级）

**目标**: 修复影响正常使用和数据一致性的缺陷

**建议分支**: `fix/stability-and-cleanup`

| 序号 | 任务 | 对应 Review 问题 |
|------|------|------------------|
| 1 | 删除服务时同步清理 `/data/flowops/services/{name}/` 目录 | #5 删除服务不清理磁盘 |
| 2 | 服务创建增加输入校验：端口范围 1-65535、服务名格式（字母数字中划线）、必填字段非空 | #7 缺少输入校验 |
| 3 | deploy catch 块将完整异常堆栈写入日志文件，方便排查 | #10 错误处理不完善 |
| 4 | 移除或注释未使用的 `docker.host` 配置项 | #11 未使用配置 |

**验收标准**:
- 删除服务后磁盘目录不存在
- 创建服务传入非法端口（如 -1、99999）返回明确错误提示，不产生 500
- 部署失败时日志文件包含完整 Java 异常堆栈

## 阶段三：部署体验优化（中优先级）

**目标**: 解决部署过程中的体验和性能问题

**建议分支**: `feat/async-deploy`

| 序号 | 任务 | 对应 Review 问题 |
|------|------|------------------|
| 1 | 部署改为异步执行，接口立即返回，前端轮询 `/api/deploy/status/{id}` 获取进度 | #6 部署阻塞请求线程 30s |
| 2 | 实现 WebSocket 日志推送（`/ws/logs`），或移除空壳代码避免误导 | #8 WebSocket 空壳 |
| 3 | 前端 Authorization header 改为 `Bearer {token}` 标准格式 | #14 非标准 Authorization |

**验收标准**:
- 调用 `/api/deploy/start` 接口在 2 秒内返回，部署状态可通过 status 接口查询
- 部署过程中前端可实时看到构建日志（WebSocket 或轮询）
- 若决定不实现 WebSocket，相关配置和空 handler 代码已移除

## 阶段四：测试与质量保障（中优先级）

**目标**: 建立基本的测试防线，防止回归

**建议分支**: `feat/test-coverage`

| 序号 | 任务 | 对应 Review 问题 |
|------|------|------------------|
| 1 | 为 AuthService / UserService 编写单元测试（含 BCrypt 验证） | #12 测试覆盖为零 |
| 2 | 为 ServiceMgmtService 编写单元测试（CRUD + 校验逻辑） | #12 |
| 3 | 为 DeployExecutorService 的文件生成逻辑编写测试（Dockerfile/nginx.conf/compose.yml 生成） | #12 |
| 4 | 为 LogService 的路径安全逻辑编写测试 | #12 + #3 |

**验收标准**:
- Service 层核心方法测试覆盖率达到 70%+
- 路径遍历相关测试用例全部通过
- CI 中能自动运行 `./mvnw test`

## 阶段五：前端与代码质量（低优先级）

**目标**: 提升前端可维护性和整体代码规范

**建议分支**: `refactor/frontend-and-cleanup`

| 序号 | 任务 | 对应 Review 问题 |
|------|------|------------------|
| 1 | 将各页面内联 `<script>` 抽取为独立 JS 文件 | #15 前端逻辑内联 |
| 2 | 统一 logback 日志配置，移除 yml 中重复的日志级别设置 | #17 logback 配置冲突 |
| 3 | deploy.sh / deploy-prod.sh 中的 IP 改为参数传入或环境变量 | #13 硬编码 IP |

## 优先级决策依据

| 阶段 | 理由 |
|------|------|
| 阶段一优先 | 安全漏洞可被直接利用，尤其在公网部署场景下，密码明文和路径遍历风险最高 |
| 阶段二次之 | 数据泄漏和 500 错误直接影响用户体验和运维信心 |
| 阶段三 | 部署阻塞 30 秒在单用户场景可接受，但多人使用时会成为瓶颈 |
| 阶段四 | 测试是长期质量保障，但不阻塞功能使用，可在功能稳定后补充 |
| 阶段五 | 代码质量提升收益是长期的，短期不影响功能 |
